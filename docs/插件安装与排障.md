# 用 DSH 插件系统安装 / 排障（dsh-pet-3d）

这份是"装进 DSH"这一层的实操记录，踩到的坑都写在这里。插件本身的动作系统见
[`packages/dsh-pet-3d/README.md`](../packages/dsh-pet-3d/README.md)。

## 一、装法（三种）

| 方式 | spec | 适用 |
|---|---|---|
| npm | `dsh-pet-3d` | 发布之后最省事 |
| **本地目录** | `link:<仓库>/packages/dsh-pet-3d` | 开发期；改完 `src/` 重新 build，刷新页面就生效 |
| tarball | `file:<仓库>/packages/dsh-pet-3d/dsh-pet-3d-1.0.4.tgz` | 稳定版本；依赖由 pnpm 真正装进 profile |

入口：**GUI 侧边栏 → 插件页**（Add plugin 接受包名+版本 / Git / tarball / 绝对路径），
或 `dsh plugin --profile <名字> add <spec>`。

⚠️ 桌面客户端的 `desktop` profile **只能**用 GUI 或 Desktop 自带的
`resources\runtime\cli\bin\dsh.cmd`（npm 全局 `dsh` 会拒绝），而且**要真退出应用**——
关窗口不算，主进程还活着，宿主不会重新组合。

装完 `pnpm add` 会把包写进 profile 的 `dependencies`，`reconcile()` 再把它加进
`dsh.profile.bundles`；它的 `cordis.patch.yml`（`dsh.bundle.patch`）里的 insert 行
就是那条插件行。**不需要手工改 profile 的 patch。**

## 二、两个"装上了但不工作"的经典形态

### 1. 客户端条目在、接口 404 —— 宿主半边没激活

判据：首页 `globalThis["__DSH_BOOT__"]` 的 `entries` 里有 `dsh-pet-3d`（客户端半边被服务），
但 `/api/pet3d/state` 404。此时**不要看 `cordis.yml`** —— 那只是 profile 根的空条目表
（`[]` + 注释），不是合成树；安装器预检留下的 dump 会在下次启动时被覆盖回去。

要拿真日志，用"隔离 profile + 同一个宿主入口"：

```powershell
# 1. 复制 profile（profile 名不能叫 desktop，那是保留名）
#    %TEMP%\dshhome-probe\profiles\probe\{package.json,pnpm-workspace.yaml,pnpm-lock.yaml,cordis.patch.yml,cordis.yml}
#    node_modules 用 junction 指回真 profile；patch 里把 webserver 端口改成 19399
$env:ELECTRON_RUN_AS_NODE = '1'
& "D:\DSHDesktop\DSH Desktop\DeepSeek Harness.exe" --expose-internals `
  "D:\DSHDesktop\DSH Desktop\resources\app.asar\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\index.js" `
  "D:\DSHDesktop\DSH Desktop\resources\app.asar\dsh" `
  "$env:TEMP\dshhome-probe\profiles\probe" `
  "D:\DSHDesktop\DSH Desktop\resources\runtime\primary-runtime" `
  "D:\DSHDesktop\DSH Desktop\resources\runtime\pnpm\bin\pnpm.mjs" `
  "D:\DSHDesktop\DSH Desktop\resources\runtime\bin"
```

stderr 里会有 `dsh: warning: N entries did not activate` 和每条的异常栈。

### 2. 真凶：`Config` 没有 standard-schema 协议

宿主 cordis 的配置解析（从 asar 里取的原文）：

```js
function resolveConfig(runtime, config) {
  if (!runtime.Config) return config
  const result = runtime.Config['~standard'].validate(config)
  …
}
```

它要的是 **standard-schema**（`~standard`）。仓库根 `node_modules/@deepseek-ai/schemastery`
曾经是手写的 **stub**（`0.0.0-dsh-pet-3d-test-stub`），造出的 schema 没有 `~standard`：

```
pet3d (dsh-pet-3d): TypeError: Cannot read properties of undefined (reading 'validate')
    at resolveConfig (.../@deepseek-ai/cordis/lib/index.js:958)
```

`link:` 安装时插件按**真实路径**解析依赖，正好落到这个 stub ⇒ 宿主半边死在配置解析阶段，
而客户端半边照常服务。**处置**：仓库里换成真包 `@deepseek-ai/schemastery@3.18.4`
（连同它的 `@deepseek-ai/cosmokit`、`@standard-schema/spec`）。长期做法是仓库跑一次
`pnpm install` —— `packages/dsh-pet-3d/package.json` 已经声明了 `^3.18.4`。

## 四、改客户端半边：`lib/` 不再入库

`lib/`（`index.js` / `client.js` / `three-vendor.js`）是**构建产物**，已移出版本库，
由 `pnpm -C packages/dsh-pet-3d build` 生成。改 `src/` 后重新构建即可，不再手打补丁。

> 历史备注：早期在个别机器上 `tsdown` 因 Smart App Control 拦截 rolldown 原生绑定而起不来，
> 当时用一组补丁脚本直接改写 `lib/`。那套脚本只在本机维护，已移出公开树。
> 现在的构建契约以 `packages/dsh-pet-3d/package.json` 的 `build` 脚本为准。

### 手打补丁时代的四条经验（保留作背景）

1. **同一个 factory 作用域**：bundle 的所有模块共享一个函数作用域，所以
   `const { useSyncExternalStore } = react;` 写两遍就
   `SyntaxError: Identifier 'useSyncExternalStore' has already been declared`，
   新模块里的 `POLL_MS` 之类的顶层常量也会跟老模块撞。症状一模一样：
   **整个客户端 "web boot: 1 entry did not activate"，宠物根本不出现**（不会只坏一部分）。
   补丁脚本的解法是把新模块各自包一层 IIFE、只把导出名提到顶层，并在打之前做一次撞名检查。
2. **能同行追加就同行追加**：改一行只在行内替换文本，行数不动，`mappings` 就不用动；
   插入整块代码才需要补空条目。
3. **别只备份 `.js`**：`client.js.map` 也要一起备份/还原，否则还原后行数对不上，
   下一次补丁会在错误的位置补映射（第一次还原就漏了 map）。
4. **多个补丁脚本的备份会互相踩**：`patch-settings-page.mjs` 的备份是"设置页之前"，而
   演出补丁打在它之后 —— 对前者 `--revert` 会把演出一起擦掉。现在的做法是：前者在还原前
   先检查 `lib/client.js` 里有没有演出补丁的指纹（`__pet3d_mod_perf_editor`），有就拒绝并
   提示改用 `patch-performances.mjs --revert` 或 git 回滚。**新增补丁脚本时照此加闸。**

### 整段替换 vs 逐处小手术

改动散在很多模块时（例如演出编排：渲染器 + PetStage + 设置页 + 数据模型），逐处打锚点
太容易断线，改成**整段替换**：`tools/patch-performances.mjs` 用仓库里的 `typescript`
把每个模块重编译一遍，替换 bundle 里对应的 `//#region src/...` 整块（新模块整块插入）。
它同时干三件事：外部 import 折成本地解构、`export` 折成 `const { ... } = __mod_x`、
打完用 TS parser 自检语法（有错就不写盘）。

这一轮踩到的新坑：**局部变量遮住全局 `performance`**。
`mountModel3d` 里加了个 `let performance` 当"正在演的演出"，结果同文件里的
`performance.now()` 全部指向它，tsc 报 `Property 'now' does not exist`。
改名 `playing` 就好 —— 但提醒一句：在这个渲染器里新增局部变量时，先想想有没有同名全局。

## 五、插件自己的设置页（settings.section）

`dsh-pet-3d` 在设置对话框里有一级页「3D 桌宠」。客户端半边的做法（照抄当前 shell 里
`@linxin666/dsh-pet` / `dsh-usage` 的写法）：

```js
ctx.inject(['slots', 'configForms'], (scoped) => {
  scoped.slots.inject('settings.section', () => scoped.slots.register({
    name: 'settings.section',
    id: 'pet3d',
    order: 145,
    label: () => '3D 桌宠',
    inject: () => ({ settings: scoped.configForms.get('pet3d') }),
  }, Pet3dSettingsSection))
})
```

- **用 `ctx.inject` 而不是顶层 `inject`**：顶层 `inject` 里缺任何服务，cordis 会把整个插件
  挂起（宠物直接不见）；`ctx.inject` 只让那一个回调等条件，宠物照常挂载。
- 客户端服务只能通过 `inject` 拿到：`inject: []` 时 `ctx.get('slots')` 也是 `undefined`
  （实测过，别以为 `get` 是全局的）。
- `configForms.get('pet3d')` 拿到的就是这条 profile 条目的 Config 表单
  （`getSnapshot()/subscribe()/mutate([{op:'set',path:['enabled'],value}])`），
  写进去会触发宿主的 `loader/volatile-update` → `syncSettings()` 即时生效。
- 开发者模式开关**故意不放进 Config**：它是浏览器界面偏好，存 `localStorage.dshPet3dDebug`
  （点宠物那一刻要同步判定，等配置往返太慢），也正好沿用了原来的调试开关。

## 六、自检清单

宿主启动后（`Get-NetTCPConnection -LocalPort 19387 -State Listen` 的 PID 应当是**新**的）：

| 检查 | 期望 |
|---|---|
| `GET /api/pet3d/state` | 200 |
| `GET /api/pet3d/models` | 200，且列出 `models/<id>` |
| `%TEMP%` 探测宿主的 stderr | `pet3d` 不在 "did not activate" 名单里 |
| GUI | 宠物出现在右下角 |
| 设置 → 3D 桌宠 | 页面能开，五个分区（显示/模型/演出/插件/开发者） |
| 开发者模式关着 | 点宠物**什么都不出现** |
| 设置 → 演出 → 试播 | 宠物身上按顺序演完，`perf=` 从 `1/N` 走到 `N/N` 再归 `-` |
| 设置 → 演出 → 保存 | 「已保存」；若提示"宿主这一版还不认识"⇒ 宿主半边还没重启 |

验收脚本（真无头 Chrome，需要 GUI 在跑）：

```sh
node tools/verify-pet-menu.mjs        # 悬浮菜单 + 互动（点按 + 仪表 + 刷新持久化）
node tools/verify-live-window.mjs     # 活体：宠物真的挂载到页面、WebGL 真的在画
node tools/check-appearance.mjs       # 配饰表与模型节点是否对得上
node tools/check-pet3d*.mjs           # 8 个离线守卫（不需要 GUI）
```

历史补丁脚本（`patch-settings-page.mjs` / `patch-performances.mjs` / `probe-acts.mjs`
等）只在本机维护过，已移出公开树；`lib/` 也不再入库，重建走 `pnpm build`。

## 七、禁用 / 卸载

- 只停这一行：GUI 插件页开关（写 profile patch 的 `disabled: true`），重启生效。
- 卸载：GUI 卸载（严格三步：移出 `dsh.profile.bundles` → 卸运行时贡献 → `pnpm remove`）。
- 手工回滚到"拷进 node_modules"的老办法：见
  `_backup/2026-10-17-before-plugin-install/MANIFEST.md`。
